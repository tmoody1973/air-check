# 015: Descriptions are written in Tarik's voice, with private sources, and can be changed only through his approval

**Decision:** The agent writes each public Mixcloud description in Tarik's own style, learned from his past Mixcloud descriptions, and may state a fact about an artist only when a Crate result (the station's music research service) backs it; those sources are shown to Tarik and never published. Tarik can edit a description before he approves it, ask the agent to rewrite it, and push a new description to a show that is already live, and nothing reaches Mixcloud without his Approve.

**Why this came up:** The first real show, 10-2-26, went public on Oct 28 at 12:31 CDT with a plain 237-character description the agent wrote with no voice and no artist context. Plan 5c found three causes: none of the station skills (the instruction files in `skills/` that teach the agent how the station works) were installed in the agent; the agent had written its own skill from failed retries, `mixcloud-package-submission`, which told it to keep the description "under 100 characters" (the title limit, not the description limit) and to open with "Mixcloud package for show [date]"; and the code's tracklist check flagged any description naming 3 or more songs, which is exactly how Tarik writes. The description is the public, permanent face of each show. Getting it wrong means either flat copy on every episode, or the opposite risk: a model-written "fact" about a real artist that nobody checked, published under Tarik's name.

**Options:**
1. **Teach the voice, source the facts, keep every change behind Approve (chosen).** Rewrite `rlr-description-safety` around Tarik's real past descriptions; allow facts only with a Crate source listed beside them; add an edit box, an agent rewrite tool and an "update a live show" path, each needing his Approve. Cost: more moving parts (a new table, two new agent tools, a publisher step that edits live shows), and a long guide sent to the model on every draft.
2. **Keep the plain, rule-only description.** Safe and short. Cost: every show goes out with copy that sounds like nobody, which is the opposite of what the description is for, and Tarik rewrites it by hand on Mixcloud each week.
3. **Let the agent write freely and have Tarik fix it on Mixcloud after posting.** No new tools. Cost: unchecked claims are public until he notices, Air Check's record no longer matches what is live, and the "only a human approves what is published" rule (Hard Rule 1) would have a hole in it.

**What we chose and why:** Option 1. The calls, and who made them:

- **No opening line about the show** (Tarik, Oct 28). The Mixcloud title already carries the show name and date, so the description starts straight in the music, like his past posts.
- **Six or more named songs counts as a pasted tracklist** (Tarik, Oct 28). That leaves room for 2 or 3 highlight songs per hour, as he writes them; the skill asks for at most 5 in total.
- **The 10-2-26 worked example in the skill keeps his voice** (Tarik). The example uses style phrases only ("smooth", "Afrobeat pulse") and no factual artist claims, because an unsourced fact in an example teaches the wrong habit (ruling R6, Claude).
- **Facts only from Crate, and the sources stay private** (joint). A fact is anything checkable: instrument, year, label, city, a collaboration. The draft carries a list of `{claim, source}` pairs (`descriptionSources`), shown on the package page as "Sources (not published)". They are part of the fingerprint (a hash of the exact package, so an approval counts only for that version) but are never sent to Mixcloud. At most 3 facts per description. Age, health and death are left out and flagged.
- **Tribute shows may mention a death** (Tarik, Oct 28, 13:29). Only when his own input marks the show a tribute, stated plainly ("honoring the late X"), sourced through Crate, with no cause, age or health, and still listed in the review flags.
- **Fix it before publish** (Tarik). The package page has an Edit description box, and the agent has a `package_revise` tool. Both work only while the package is waiting for review, and both change the fingerprint, so Approve only works after Tarik has seen the new text.
- **Updating a live show** (Tarik asked for it once 10-2-26 was live; the design was joint). A new description for a published show is a separate "description update" record. Tarik or the agent proposes it; only a signed-in person approves it; the publisher then sends only the description to Mixcloud's edit address. That address is built from the show's own receipt link, never from anything typed or proposed, so an update cannot land on the wrong show. Title, tags, cover and tracklist do not change. The package record itself is never rewritten: what Mixcloud shows is the latest pushed update.
- **The skill text is delivered in code, not left for the agent to find** (Claude, after the live test). Installing the skill was not enough: in the 14:42 CDT live test the agent rewrote 10-2-26 as a near-copy of the old text with the old opening line, and Hermes's usage file had no entry for the skill, so it had never opened it. The skill text is now compiled into the code and sent with every draft request and with every `package_get` result (the agent's read-only tool for looking at a package). A test fails if the copy drifts from `skills/rlr-description-safety/SKILL.md`. The retry at 15:51 CDT came out in Tarik's voice.

**A note on Hard Rule 5 (email and notes are untrusted).** `package_revise` gives the agent a new place to write. Anything the agent read (an email, show notes, a web result) can now shape a proposed description. It stays a proposal: on a package waiting for review it changes the text and resets the fingerprint, so Approve needs Tarik again; on a live show it only creates a proposed update. The checks on public text (length, time-relative phrases, private terms, tracklist paste) run on every proposal, and nothing is published without a signed-in person approving that exact text.

**What we gave up:**
- About 8,000 characters (roughly 2,000 tokens) of guide on every draft request and every `package_get` read, paid in model cost and time on each run.
- The agent leans on the worked example's wording. The first in-voice retry was close to the skill's 10-2-26 example and ended on the skill's stock closing phrase, "crafting a seamless flow of discovery and depth", so descriptions may start to sound alike.
- Facts only from Crate means fewer facts. When Crate has nothing solid on an artist, the description says nothing checkable about them, even when Tarik knows the story.
- An approved update cannot be withdrawn while Mixcloud is disconnected; it waits and goes out after reconnecting.
- More to run: a new table, two new agent tools and a second kind of publisher job, each with tests to keep.

**How we'll know if this was right:** Through Dec 15, every published description passes the code's checks, names 5 or fewer songs, and has a source on the package page for every checkable claim; no description update reaches Mixcloud without a signed-in Approve on that exact text (the Hard Rule 1 tests pin this); `nemohermes airc skill list` shows no agent-made description skill coming back; and Tarik edits the agent's description by hand on fewer than half the shows.
