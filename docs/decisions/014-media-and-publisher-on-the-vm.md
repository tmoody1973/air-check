# 014: Audio encoding and Mixcloud publishing run as two small services on the VM

**Decision:** Two new programs run on the Nebius VM (the one cloud machine Air Check deploys to), next to the relay. The media service joins a show's two hour-long WAV files into one MP3 with ffmpeg (the standard command-line audio and video tool). The publisher uploads approved shows to Mixcloud. Each talks to Convex (the hosted database and backend Air Check runs on) with its own secret token that works only for its own short list of functions. The Mixcloud login token lives in a locked file on the VM that only the publisher reads; Convex never holds it.

**Why this came up:** Plan 5 is where a drafted package becomes a real public show. That needs two jobs nobody has built yet: turning two large WAV files into the MP3 Tarik previews and approves, and uploading the approved package to Mixcloud. Both sit right next to the approval gate (the code that makes sure only a package Tarik approved can be published, Hard Rule 1). If either job could approve something, post something twice, or leak the Mixcloud login, a show could go public without Tarik, appear twice, or the station's Mixcloud account could be taken over. Decision 004 had said the audio join would run as a Nebius Serverless Job; on Oct 27 Tarik reversed that.

**Options:**
1. **Both on the VM, each with its own token (chosen).** The media service and the publisher are host programs under systemd (the VM's service manager), built like the relay. `MEDIA_TOKEN` lets the media service list packages waiting for audio, attach the finished MP3's fingerprint, report shows whose audio is missing, and list MP3s it may delete. `PUBLISHER_TOKEN` lets the publisher read the approved queue, claim one package, record the result and report Mixcloud's connection state. Neither token can approve anything, and each token is refused by the other service's functions and by the relay's and the agent's. Cost: the VM does the encoding (a few minutes of CPU and about 3 GB of scratch disk per show), and two more services to keep running and watch.
2. **Audio on a Nebius Serverless Job (a task that starts only when needed and then shuts down), publisher on the VM.** This was decision 004. Cost: the large WAV files have to be shipped into and out of the job, its disk limits for about 1.26 GB of input were never verified (spike V10 never ran), and it adds a second place to deploy and debug days before the deadline.
3. **Everything inside the console (the Next.js web app).** No new services. Cost: the public-facing app would hold the Mixcloud login and run hour-long encodes inside web requests, and a bug in any console page would sit one step from the upload.

**What we chose and why:** Option 1. Running ffmpeg on the VM instead of a Serverless Job was Tarik's call on Oct 27; the separate-token design follows the relay's pattern (decision 012), which already works. Details that came with it:

- **The agent's audio guesses are never trusted.** The agent drafts a package without knowing which audio files exist, so its hour ids are placeholders. When the media service attaches the MP3, the actual WAV filenames it joined replace them, in the same database step that attaches the MP3's fingerprint (a hash, a short code that changes if even one byte of the file changes).
- **The publisher can only claim and report.** A test reads the publisher's code and fails if it changes a package any other way than through the gate's "claim an approved package" and "record the result" steps. Another test proves a package that never went through Tarik's Approve cannot be claimed.
- **No double posts.** If the publisher stops in the middle of an upload, on restart every package still marked `publishing` becomes `outcome_unknown` ("we don't know if it posted"), never back to approved. Tarik checks Mixcloud and decides.
- **The Mixcloud token lives in a file, not the database.** The console's "Connect Mixcloud" button runs Mixcloud's sign-in in the browser; the console's server writes the resulting token to a file on the VM that only the console can write and only the publisher can read (mode 640). Convex stores only whether Mixcloud is connected, the account name, when, and the last error. This keeps Hard Rule 2: no Mixcloud credential in the agent, the relay or Convex.
- **Cover art is part of what Tarik approves.** Picking a different cover changes the package's fingerprint, so Tarik approves the package as it will actually look. A package with no cover keeps exactly the fingerprint it had before covers existed, so packages already waiting for review do not flip to "changed". With no cover picked, the publisher uses the station's standard cover.

**What we gave up:** No Nebius Serverless story for the hackathon's Personal AI Track; Air Check uses Nebius for the VM and the models only. The VM does the encoding, so a show being encoded competes for CPU and disk with the agent and the console, and one show is processed at a time. The Mixcloud token sits on the VM's disk: anyone who gets root on the VM gets the token (Mixcloud lets Tarik revoke it). A show whose upload was cut off waits for Tarik even when it actually posted fine.

**How we'll know if this was right:** A real show's two WAVs dropped in the VM inbox become an approvable package with a playable MP3 and no manual step. The first approved upload (unlisted, as a test) appears on Mixcloud once, with title, tags, description, tracklist and cover. Through Dec 15: no show posts twice, no package reaches Mixcloud without Tarik's Approve, no Mixcloud token ever appears in Convex's environment variables or tables, and the VM never runs out of disk during an encode.
